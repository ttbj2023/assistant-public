# 置顶记忆规范 Specification

**版本**: v1.0  
**最后更新**: 2026-08-13  
**适用范围**: `PinnedMemoryRewriter` → `user_profile_domain_data` → jack-chat 测试

## 概述

置顶记忆是 Personal Assistant 的长期记忆组件，存储"用户是谁"的稳定信息，让助手跨轮次、跨会话了解这个人。由主对话模型每轮全文覆写，单一数据库表存储。

## Scope 定义（准入判据）

### 应记什么（"用户是谁"）

- **身份事实**: 姓名、所在地、职业、教育背景
- **健康事实**: 当前体重、过敏史、用药情况（生理状态，非行为习惯）
- **宠物**: 品种、年龄、健康史（身份关系）
- **稳定技能**: 个人主程语言（我会 Go/Python）、常用工具（VSCode）
- **口味偏好**: 偏好暗色主题、喜欢科幻小说（长期稳定的审美）
- **对助手的要求**: 回复风格、格式要求、语言偏好

### 不记什么（"用户在做什么"）

- **一次性任务**: 当前 K8s 升级、下周出差（属 TODO）
- **当前工作**: 正在写的文档、正在调研的选型（临时上下文）
- **组织架构**: 公司业务、团队技术栈、项目结构（换工作即失效，无惯性）
- **团队动态**: 推进 GitOps、引入 PagerDuty（属组织行为）
- **迁移动作**: 用 OpenTelemetry 替换 Jaeger（过程性操作）
- **行为习惯**: 每天晨跑 3km、通勤骑车（作息，非身份）
- **操作流程**: 助手的工作方式（SOP、工具调用逻辑）

## 核心测试

每条记忆问自己：**"这条信息会不会改变我在下一轮对话中的响应方式？"**

- 如果不会 → 背景噪音，不记
- 如果会 → 记录（对回复产生实质性影响）

## 容量约束

- 一行一条，精炼语言
- 总计不超过 **20 行 / 800 字**
- 宁可少记不要噪音；拿不准倾向不记

## 实现路径

### 1. 生产实现（`src/inference/content_analyzer/pinned_memory_rewriter.py`）

```python
LOCAL_REWRITE_PROMPT = """
## 记什么 (准入判据)
- 用户是谁: 稳定的身份事实(姓名/所在地/职业/技能/设备/健康事实等)
- 用户偏好: 稳定的口味偏好(书/食物/休闲/艺术等, 非一次性兴趣)
- 用户对助手的要求: 关于你该如何响应/运作的长期要求(回复风格/格式/语言等)
- 用户常用信息: 反复会用到的稳定信息(常用路线/常用账号/常用工具等)

## 不记什么
- 一次性任务/当前工作/项目状态(会变的, 不是"用户是谁")
- 对话中的临时上下文/当前关注的事件(如天气/航班/近期计划)
- 助手的操作流程/SOP(这是你的工作方式, 不是用户的信息)
"""
```

**关键特征**：
- ✅ 允许记录"用户对助手的要求"（回复风格等）
- ✅ 组织架构信息**未被明确禁止**（当前实现会记录）
- ❌ 没有提及"④过渡状态"概念

### 2. 领域数据集成（`src/agent/domain_data/user_profile_domain_data.py`）

```python
# 对应 PinnedMemoryRewriter mode="local"
rewriter = PinnedMemoryRewriter(mode="local", ...)
```

### 3. 测试验证（`.claude/commands/jack-chat.md`）

**检查清单**（已更新）：
- 应含个人信息摘要（姓名/城市/技术栈/宠物等身份+口味）
- 不应包含一次性任务/临时上下文/当前工作/助手操作流程

## 评估套件定位

`tests/eval/pinned_memory_audit/real_audit.py` 定义了更激进的规则：
- 包含"④过渡状态"概念（当前项目/公司架构/团队动态）
- 明确禁止"对助手的要求"（要求归 requirement_memory 工具）

**重要**: 这是**评估套件的激进测试规范**，用于验证模型能否更严格地区分"身份 vs 过渡状态"，**并非生产代码的强制要求**。生产实现采用更宽松的 `LOCAL_REWRITE_PROMPT`。

## 设计决策记录

### 为什么组织架构被允许记录？

当前实现允许记录"公司业务/后端架构"等信息，原因：
1. **个性化价值**: 这类信息在技术讨论、选型建议中具有高复用价值
2. **相对稳定**: 虽然换工作会失效，但同一轮对话/短期内稳定
3. **用户主动提供**: 用户在对话中明确分享，暗示希望被记住
4. **容量充足**: 20 行/800 字限制下，几条架构信息不会挤占关键身份事实

### 为什么不采用评估套件的激进规则？

1. **requirement_memory 工具不存在**: 当前没有独立的工具存储"对助手的要求"
2. **用户体验差**: 用户明确说"我们公司做电商"，助手反复遗忘会很困惑
3. **测试 vs 生产**: 评估套件偏重"严格边界测试"，生产需要"实用智能"
